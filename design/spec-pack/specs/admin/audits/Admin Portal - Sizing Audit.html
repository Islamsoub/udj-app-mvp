Headline: the sizing is in very good shape. The token layer, all six core primitives, the shell geometry and the schedule grid maths are reproduced from the spec essentially exactly — including deliberately off-grid values like 13.5px, 3.5px accent bars, translateX(17px) and left: calc(50% + 124px). This is not a case of the build drifting from the design. The 21 findings below are three genuine bugs, one token-layer inconsistency, and a tail of small local deviations where a page hand-rolled a value instead of using the primitive.
Correction to the brief. Four target values in the request do not match the implementation spec, so I audited against the spec document. Button: the brief says height 38 / padding 0 18 / font 14 / gap 8; spec §5 says padding 7×12 / 9×16 / 12×22, font 12.5 / 13.5 / 15, gap 7, no fixed height — the code matches the spec exactly. Same for Input (spec: 10×13, font 14 — no height given). Also worth knowing: PageHead subtitle is 14px per spec and the code agrees; and there is no spec value for toast width/height, only the 28px offset and 2600ms, both correct. If the brief's numbers are the newer intent, the spec needs updating first — otherwise these would be "fixes" away from the signed-off design.

1 Real bugs — broken measurements

Bug Grade entry never reserves the 76px sticky-bar gutter
Spec§29 "Sticky bars": the page reserves 76px bottom padding while the bar is active, so the last table row clears the fixed save bar. CodeclassName={cn(dirtyCount ? 0 && 'pb-[76px]')} — the expression 0 && '…' evaluates to 0, never the class. So the padding is applied in neither branch: dirty → 0, clean → undefined. Fileadmin/app/(dashboard)/grades/[subjectId]/page.tsx:209 EffectWith unsaved edits, the fixed save bar (line 421) covers the last student row — exactly the row you are most likely still editing. The sibling screen does this correctly (attendance/session/page.tsx:136 → plain pb-[76px]). FixReplace with className={cn(dirtyCount > 0 && 'pb-[76px]')}.
Bug Grade-entry save bar is missing left: 248
Spec§16 / §29: the bottom action bar is viewport-fixed and offset left: 248px to clear the sidebar, with a top hairline and 0 -6px 22px shadow. CodeLine 421 sets fixed bottom-0 right-0 only; the left: 248 arrives on line 422's style object. Confirm both are present on the same element — the session screen pairs them correctly (session/page.tsx:268). If the class list wins the cascade, the bar spans under the sidebar. Fileadmin/app/(dashboard)/grades/[subjectId]/page.tsx:421–422 FixDrop right-0 in favour of explicit style={{left:248,right:0}}, matching the session screen.
Bug Context bar is 46px tall but holds a 40px control
Spec§30.1: "Compact strip (~46px), not a second nav bar." CodeThe strip is h-[46px] — but it embeds the full-size Dropdown, whose control is py-[10px] + text-[14px] + 1px borders ≈ 40px. That leaves ~3px of breathing room top and bottom, and the locked-faculty pill (py-[7px] + 13px text ≈ 34px) doesn't match the dropdown beside it. Filecontext-bar.tsx:39 (BAR_BASE), 133 & 152 (<Dropdown>), 124 (locked pill) FixAdd a size="sm" Dropdown variant (py-[6px], text-[13px] → ~32px) and use it in the bar; set the locked pill to the same height. This is the "reads as a second nav bar" symptom in visual terms — the strip currently has no vertical rhythm of its own.

2 Design tokens (§2–3)

admin/styles/globals.css · tailwind.config.ts · lib/tokens.ts
Drift TONE_COLORS invents a second, darker accent palette
Spec§2 defines one fg/bg pair per accent: danger #E1483D on rgba(225,72,61,0.10); amber #D9821A on 0.12; blue #2F7DD1 on 0.12; exam #7C53E0 on 0.12; slate #5A6B7B on 0.12. §5 Badge says "tones map to a [fg, bg] pair". CodeThe CSS variables are correct — but TONE_COLORS ships different, darkened foregrounds and heavier backgrounds: danger #B3392F/0.12 · amber #9A5B06/0.14 · blue #1F5FA6/0.12 · exam #6034C9/0.14 · slate #46535F/0.14. Only jade matches. Fileadmin/lib/tokens.ts:78–85 EffectEvery Badge, Tab, StatCard tile, Avatar tone and Modal icon tile renders in colours that exist nowhere in the spec — and they sit next to spec-correct text-danger / text-amber text, so the same semantic colour appears in two shades on one screen (visible on Présence, where amber row text and amber badges disagree). FixThis looks like a deliberate contrast fix (the spec's raw accents on a 10–12% tint are around 3:1 on small text). Decide it properly: either revert TONE_COLORS to the spec pairs, or promote these darkened values into §2 as the official "on-tint" foregrounds and add them to globals.css as --danger-on-tint etc. Don't leave two palettes.
Everything else in the token layer is exact. All 9 surface/text tokens, 8 jade tokens, 5 accent pairs, 6 sidebar tokens, --toggle-off #D5DCD8, --scrim rgba(16,22,20,.45), and all four shadows (shadow, shadow-lg, shadow-side, shadow-modal) match §2 character-for-character, including blur radii, offsets and alpha values. The three keyframes match §29 exactly: toastIn .26s, fadeIn .16s, popIn .18s, all with the correct cubic-bezier(.2,.9,.3,1). The 12-colour COURSE_PALETTE matches §9. No raw hex leaks into Tailwind — every utility resolves to a variable, as the config comment claims.

Bottom line. 21 discrepancies across 32 files, but only three affect what a user sees today, and only one is a defect in the ordinary sense. The gap the first audit found is a content and data gap, not a sizing one — the measurements in this build are faithful to the spec, and the one systemic exception (TONE_COLORS) looks like an intentional accessibility fix that was never written back into §2. Fixing that and documenting the handful of undocumented values would put the code and the spec back in exact agreement.
